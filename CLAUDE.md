# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`teach-imgui`: native Windows desktop apps (Go + Dear ImGui via `cimgui-go`, GLFW + OpenGL3) for teaching AFVI colour-inspection machines. Single Go module `afvi/teach-imgui` with two GUI programs plus a command-line camera simulator:

- `cmd/teach-imgui` -> `bin/teach-imgui.exe`, the teaching program: align tab (ROIs/occlusion) and defect-detection tab (channel, camera snap source, F1 detection parameters, learn intervals, results, probe). No painting tools, no light tab, and it never draws the simulated stroke outlines (they are the answer).
- `cmd/camera-gui` -> `bin/camera-gui.exe`, the camera studio (window title "Color AFVI Camera Studio"): light & GV tab and defect-synthesis tab (render channel, virtual good unit, brush, frame tool, colour, amplitude, profile, random defects, sensor noise, view test/golden/diff, selection palette + floating editor, stroke outlines visible). It never runs the inspection; its Output column saves the current scenario by running `camera.exe`.
- `cmd/camera` -> `bin/camera.exe`, the command-line camera simulator used by both GUIs as a subprocess.

The two GUIs also talk to each other over a live link (`internal/link`, docs/LINK.md): the studio publishes its scenario and serves frames, the teach program follows it and inspects the live frames, so nothing has to go through image files; the teach program saves a session (snap folder + `inspect.json`) when asked.

Docs in `README.md` and `docs/` are written in Chinese.

Development happens on WSL2/Linux and the app is **cross-compiled to Windows**; it only runs on Windows (fonts are loaded from `C:\Windows\Fonts`, screenshots use Win32 APIs).

## Commands

```bash
./scripts/build-wsl.sh              # gofmt check -> go vet -> pure-Go tests -> build bin/teach-imgui.exe, bin/camera-gui.exe and bin/camera.exe
./scripts/build-wsl.sh --offline    # same with GOPROXY=off (needs a warm module cache)

# Pure-Go packages test natively on Linux, no cgo needed:
CGO_ENABLED=0 GOOS=linux go test ./internal/config/... ./internal/core/... ./internal/inspect/... ./internal/model/... ./internal/snap/... ./internal/camera/... ./internal/link/...
CGO_ENABLED=0 GOOS=linux go test ./internal/core -run TestUnwarpPointInvertsWarpPoint -v   # single test

command gofmt -l cmd internal       # the build script fails if this prints anything
```

- In the maintainer's interactive zsh, `gofmt` is aliased to `gofumpt -l -w .`, which **rewrites files in the working directory**. Always write `command gofmt ...` (the build script is unaffected).

- `go vet ./...` and `go build` touch `internal/app` (cgo). They need the cross environment the build script exports: `CGO_ENABLED=1 GOOS=windows GOARCH=amd64 CC=x86_64-w64-mingw32-gcc CXX=x86_64-w64-mingw32-g++` (apt `mingw-w64`). Prefer running them through `build-wsl.sh`. First cgo build takes 2-3 min.
- `scripts/build.ps1` is the native-Windows equivalent (MinGW from scoop; links statically with `-extldflags=-static`, whereas the WSL script uses `-H windowsgui`). It also builds `bin\camera.exe` (pure Go, `CGO_ENABLED=0`) and runs the same pure-Go test set. Keep the two scripts' gofmt/vet/test steps in sync.
- `internal/app` has only headless tests (`profile_test.go`: profile panels, per-profile self-test step sets, detect/author render paths, the studio Output save through `camera.exe`, font scaling; `live_test.go`: a studio and a teach program joined over a loopback socket, adoption of revisions, byte equality with the studio render and with `camera.exe`, save/load round trip, model mismatch, reconnect, publish debounce, `-link` address resolution). They need no window but cgo, so cross-compile and run the test binary through Windows interop: `go test -c -o /tmp/app.test.exe ./internal/app` (with the cross environment), then `AFVI_CAMERA_EXE="$(wslpath -w bin/camera.exe)" WSLENV=AFVI_CAMERA_EXE /tmp/app.test.exe -test.v` (`TestStudioSaveCapture` skips without camera.exe). Everything that draws is verified with `bin\teach-imgui.exe -selftest -out <dir>` and `bin\camera-gui.exe -selftest -out <dir>` (or `build.ps1 -Selftest`), which walk every tab x theme x language, inject synthetic mouse input at the viewer layer (`viewerInput`, including `shift`), assert results per step, and write screenshots plus `native-metrics.json` (`errors` must be `null`). The steps are filtered per program (`filterSteps`): the teach program runs align + detection steps, the studio runs light + synthesis steps plus a `studio-save` step that writes `<dir>\studio-capture` through `camera.exe` and verifies it (sha256 of the pixels). Add a step to `NewSelftest` for new interactions, and to `studioOnlySteps` / `teachOnlySteps` when it belongs to one program. Both self-tests need `bin\camera.exe` next to the executable (the snap and studio-save steps run it) and have a 300 s time limit. The self-tests do not open the live link unless `-link` is given explicitly; with it, the teach self-test gets a last `live` step that follows a studio running idle in another process on that address (`camera-gui.exe -link 127.0.0.1:47651`, then `teach-imgui.exe -selftest -link 127.0.0.1:47651`).
- From WSL you can run that selftest through Windows interop when a git-ignored `reference/` directory exists: `./bin/teach-imgui.exe -selftest -ref "$(wslpath -w "$PWD/reference")" -out "$(wslpath -w <outdir>)"`. It opens a real window for about a minute; an occasional "empty client rect 0x0" failure means the window was hidden or minimized, so just rerun.
- Useful run flags (both GUIs): `-config`, `-machine`, `-ref`, `-theme`, `-lang`, `-model FM1/<id>`, `-fontsize <10-28>` (UI font size in pixels, default 16), `-link <addr>|off` (live link address, default `127.0.0.1:47631`, env `AFVI_LINK`; the studio listens, the teach program dials; a bare port means `127.0.0.1:<port>`), `-exitafter 12s` (see `app.Run`).

## Architecture

Four packages with a strict dependency direction `app -> core, inspect, config`:

- **`internal/config`**: pure Go, hand-written TOML-subset reader/writer for `afvi.toml` (machines with FM1/FM2/BM data roots). Relative paths resolve against the config file's directory (`Config.ResolvePath`). Lookup order: `-config` -> `AFVI_CONFIG` -> next to exe -> working dir. With no file, `app.Run` synthesises a `REFERENCE` machine from `FindReferenceRoot`. `afvi.toml` and `reference/` are git-ignored (machine-specific); `configs/afvi.example.toml` is the template.
- **`internal/core`**: pure Go image/algorithm code for the **simulation** (gray, rng, light, warp, align, defect strokes/painting/rendering, `RenderDefectPair`, `RenderGoodSample` = defect-free sample with sensor noise). It is a **bit-for-bit port of the TypeScript `teach-core`** from a separate repo (DMT_AFVI_Color_Parameter_AutoParse). Tests such as `TestRngMatchesTS` / `TestHashGrainMatchesTS` pin golden values from the TS implementation, and helpers like `ClampByte` deliberately mimic JS `Math.round`. Don't "improve" numerics or RNG/hash behaviour without checking against the TS reference. Keep it free of cgo and UI imports so it stays testable on Linux. The old golden-diff detection (`DetectDefects`, `ProbeArea`, `DefectParams`, `DefectReport`, thresholds, `MaterialMask`) was removed; detection now lives in `internal/inspect`. It also holds `ApplyProductVariation` / `NewProductLightScene` (`product.go`, virtual good unit baked into `LightScene.Texture`, off in all other core APIs) and `strokegeom.go` (stroke bounds / distance / point-in-shape helpers).
- **`internal/inspect`**: the inspection algorithm, standard library only (it also reads and writes the parameter file `inspect.json` in `paramsio.go`: `Params` has a named-material JSON form, `ParamsFile` holds per-channel `{learned, params}`, `WriteParamsFile`/`ReadParamsFile` validate). `Inspect(img, regions, params)` receives only the 8-bit gray test image and the product's *design* material map (unpainted `Scene.Material`: base 0, SR 1, open 2, metal 3) — never the golden/clean render, the simulated strokes or any simulation type. Per material there is an accepted GV interval `[Low, High]`; pixels outside it are flagged (above High = bright, below Low = dark), flagged pixels are grown by `Size/2` and touching groups merge into one defect, and groups with fewer than `MinArea` flagged pixels are dropped. `Params.EdgeMargin` (0..64 px) ignores every pixel whose Chebyshev distance to a pixel of a different material is at most that value: such pixels take no part in per-material statistics, `Learn`, flagging or probes (the machine's "Margine"); the library default is 0 and the app default is `defaultEdgeMargin = 6`. `Params.BackgroundRadius` (0..16, library default 0 = the plain per-material interval) together with the per-material `MaterialParams.LocalBackground` switch (true for every material in `DefaultParams`, but the app's default configuration, `newInspectParams` in the defect-product helper with `defaultBackgroundRadius = 2`, enables it for Metal only) selects the local background mode implemented in the inspect package's background file: a valid pixel of such a material is compared with the median of the same-material valid pixels in its (2r+1)² window (Huang sliding histogram), the accepted interval applies to f = (v − b) + mean(b) clamped to 0..255, statistics/Learn/Probe of that material use f, `Defect.PeakGV`/`MeanGV` stay raw; the median follows hard-edged plateaus, so large flat defects are absorbed as background (that is why SR keeps the global interval); changing the radius or the switch re-learns like the edge margin. `core` and `inspect` must never import each other; this is guarded by `internal/inspect/isolation_test.go` (inspect imports only the standard library, and no file in `internal/core` imports inspect). `internal/app/inspect_bridge.go` is the only place that converts between the two.
- **`internal/model`**: pure Go model scanning/loading moved out of the cgo package `internal/app` (`ScanMachine`, `LoadScene`, `Scene`, `ResolveConfig`, `FindModel`); `internal/app` keeps thin aliases. `internal/model/modeltest` writes a tiny synthetic reference tree for tests.
- **`internal/snap`**: the shared capture format, standard library plus `internal/core` only. A capture is a folder with a description file `snap.json` (also readable as a single `*.json` or gzip `*.json.gz`; unknown fields ignored; `version` 1) plus 8-bit gray PNGs `red.png`, `green.png`, `blue.png` (kind `test`) and `red-good.png`... (kind `good`, a defect-free sample used for learning). `snap.json` carries all meta information (`format` `afvi-snap`, `version`, `producer`, `created`, `model` with the absolute layer paths, `width`, `height`, `recipe` with product/light/noise/defects/sceneStrokes, and `images` with channel, kind, file, size and the sha256 of the raw pixels, verified on read). With `-mode recipe` only the description is written (a few KB, dense when gzip-compressed) and any consumer can re-synthesise identical pixels deterministically.
- **`internal/link`**: the live link contract between the two GUIs, standard library plus `internal/snap`; docs/LINK.md is the spec. Framed TCP (20-byte header `AFVL`/version/type/id/JSON length/body length, JSON part + binary body). The studio side is `Server` (`Listen`, `Publish(meta, render) rev`, `Peers`, `Rev`, `Close`): it pushes the current `Scene{Rev, Meta}` (a `snap.Meta` without images) after the hello and after every publish (coalesced) and answers `getFrame{rev, channel, kind}` with raw 8-bit gray frames, `kind` = `test` | `good` | `golden` (the clean render, only for the golden/diff views); a request for a revision that is no longer current gets `stale` (also re-checked after rendering), at most 2 renders run at once and 4 frames per revision are cached. The teach side is `Client` (`Dial`, `Scene`, `Updates`, `Frame(ctx, rev, channel, kind)`, `Done`, `Err`); reconnecting is the caller's policy (the app redials every 2 s). A studio process has a random session id, revisions are only comparable within one. Loopback only, no authentication.
- **`internal/camera` + `cmd/camera`**: the camera simulator, pure Go (`CGO_ENABLED=0`, builds and runs on Linux and Windows). `DefaultRecipe`, `Render`, `Save`, `SceneFromMeta` and the command line `Main`. The default scenario equals the app default: nominal virtual good unit, red/green/blue lights at 512, no sensor noise, 10 tiny bright specks (seed 7) from the shared generator `core.DefaultTinyDefects` that the app also uses. Command line: `camera -ref <reference> -list`; `camera -ref <reference> -model FM1/25fbo015-15 -channels red,green,blue|all [-good] [-count N -seed N -strength X -no-product -noise-read S -noise-shot G -noise-seed N] -out <folder>`; `-mode recipe -out desc.json.gz`; `-in <snap.json|desc.json.gz|folder> -out <folder> -channels blue` (re-render a description; without `-model` the layer paths stored in the description are used; an output folder that already holds the same recipe keeps its earlier images); `-info <path>`; `-config/-machine/-ref` as in the teach app. Exit codes: 0 ok, 1 runtime failure, 2 usage.
- **`internal/app`**: the ImGui UI; the only cgo-dependent package.
- **`internal/appicon` + `cmd/mkicon`**: the application icons, pure Go (standard library only). `appicon.Render(kind, size)` paints the Win32-classic icon of the teach program or the studio with a small painter's-algorithm rasteriser (4x4 supersampling), `appicon.ICO(kind)` packs the sizes in `Sizes` as a PNG-in-ICO file, `go run ./cmd/mkicon` writes `assets/icons/{teach,studio}.ico` (committed). `cmd/teach-imgui/teach.rc` and `cmd/camera-gui/studio.rc` name the icon `GLFW_ICON` (GLFW's window class icon) and group 1 (Explorer); both build scripts compile them with windres into git-ignored `rsrc_windows_amd64.syso` files that the Go linker picks up. Tests in `internal/appicon` pin pixels and the ICO structure.

### How `internal/app` fits together

- **Manual control** (`manual.go`): the teaching program's defect tab has a "Manual control" section. `DefectPanel.manual` (default off) makes `requestRun` refresh the test image only and clear `lastReport`; `requestInspect` (Inspect button, F5, and `requestRelearn`) sets `inspectNow` so the next run learns and inspects even in manual mode. "Load Image..." (`pickImageFile`: `GetOpenFileNameW` in `filedlg_windows.go`, a stub elsewhere) loads a PNG/JPEG/BMP/TIFF through `readGrayImage` into `DefectPanel.user` (size must equal the model); it has priority over live, snap and simulation sources, calls `leaveLive`, is dropped by `clearUserImage` (new model, snap, snap load, live adoption, "Use simulation") and is learned from itself because it has no good sample. Inspection still receives only the gray test image and the design material map.

- **Panels** (`Panel` interface in `app.go`): each `panel_*.go` registers itself from `init()` via `registerPanel(order, ctor, profiles...)` (0 light, 1 align, 2 defect) and also registers its translations from `init()` via `Messages(zh, en, ko)`. Passing no profiles registers the panel for every program; passing profiles restricts it to those. Adding a tab needs no change to `App`.
- **Profiles** (`profile.go`): `Profile` selects which program is running, `ProfileTeach` or `ProfileStudio`; `Profile.WindowTitle()` gives the OS window title (also used by the self-test to find the window for screenshots) and `Profile.defectMode()` says what the shared `DefectPanel` does: `modeDetect` (teach: adjust inspection parameters and inspect the test image, no painting tools, never draws the simulated stroke outlines) or `modeAuthor` (studio: paint the synthetic defects, product and noise and write captures, never runs the inspection). The teach program has the align and defect-detection tabs; the studio has the light & GV and defect-synthesis tabs.
- **Font scaling** (`scale.go`): layout constants were designed for a 13 px font; the UI font is larger now, so every hard-coded pixel length is passed through `sc()` (and `SetFontPx` sets the size once before the first frame, clamped to 10..28 px, default 16). New pixel constants must go through `sc()` too.
- **Shared state** lives on `App`: loaded `Scene` (treat as read-only), shared `core.LightSetting`, the single `Viewer`, and `Jobs`. Panels get `ModelLoaded` / `LightChanged` / `Activate` / `Deactivate` callbacks; the viewer shows one texture at a time and the active panel supplies overlays and receives left-drags in image coordinates (`Pointer`).
- **Threading model** (`jobs.go`): everything UI runs on the main OS thread (`main.go` locks it; GLFW/OpenGL require that). Heavy work goes through `App.Jobs.Run(key, work)`, where `work` runs on a goroutine and returns an *apply closure* that `Jobs.Poll` executes on the UI thread. Only apply closures may touch app/panel state. Each key has at most one job in flight, and a newer submission replaces the pending one (so slider drags render the latest value only). Panics in `work` are recovered and surfaced in the status bar.
- **Layout** (`App.Frame`): a fixed layout of non-movable, non-resizable ImGui windows positioned with `place(...)` inside the main viewport (menu bar, toolbar, tab strip, left panel, viewer, right panel, status bar). `loop` in `run.go` explicitly clears `ConfigFlagsViewportsEnable`, because otherwise edge panels become separate OS windows.
- **Win32 Classic skin**: `win32.go` (`DrawEdge`, `Caption`, `HotText` bevel primitives), `theme.go` (palettes, light/dark), and `widgets.go` (owner-drawn buttons, `GroupBox`, `TabStrip`, label-left sliders/inputs). Use these rather than stock ImGui widgets so the look stays consistent.
- **i18n** (`i18n.go`): `T(key, "name", value, ...)` falls back from the current language to `zh`, then to the key itself. Widgets take a stable `id` separate from the translated label so state survives language switches; keep that convention when adding controls. Add every new key to all three dictionaries (zh, en, ko).
- **Model data** (`models.go`): `ScanMachine` walks each host root's `PxRepository/<model>` (needs `Metal.tif`, `SR.tif`, `Open.tif` and a version folder containing `MEDIAN`; prefers version 2.0 for FM, 3.5 for BM) and picks up `PxInventory/INSPECT_SPEC/.../AlignSpec.xml` for machine ROIs. `LoadScene` decodes the four TIFFs in parallel.
- **Viewer input contract** (`viewer.go`): wheel zooms (1.2 per notch); Shift+left click zooms in and Shift+right click zooms out (`clickZoomStep`, never reaches the panel); unclaimed left drags and middle/right drags pan; a right click with under 4 px movement is reported to `Panel.Pointer` as `PointerRightClick`. Double click fits the view unless a tool is dragging or a panel called `Viewer.SetDoubleClickFit(false)` (multi-click tools such as the pen do this while a polygon is open). Panels whose `Pointer` always returns true (light) must keep ignoring unknown `PointerKind` values.
- **Frame tool and dialogs**: `shapetool.go` holds the panel-independent `FrameTool` (rectangle, ellipse, Photoshop-style pen closed by right click). A panel may additionally implement `DialogPanel` (`DrawDialogs`, called from `App.Frame` for the active panel); the defect tab uses it for the F1 detection-parameter window.
- **Defect panel flow**: in `modeDetect` (teach), `requestRun` renders the test image through `core` (`RenderDefectPair`), auto-learns the per-channel intervals the first time a model/channel is shown (or on "重新学习区间") by rendering a defect-free good sample with `RenderGoodSample` and taking `Low/High = mean ∓ learnK·σ` per enabled material, then calls `inspect.Inspect` with the test image and the design material map. The test image can instead come from a camera snap (`snap_source.go`: the panel writes the current scenario as a description, runs `camera.exe`, reads the PNG back and inspects it; a stale capture is reported until the next snap, and channel switches fetch the missing channel on demand), while the golden image always stays a local clean render. The golden image only feeds the display views (golden/diff); inspection never receives it. Changing the light does not re-learn, so over-/under-kill becomes visible. In `modeAuthor` (studio) the panel only renders the synthetic scene and never calls `inspect`.
- **Live link** (`live.go`, `live_studio.go`, `live_teach.go`, `teach_save.go`, `live_selftest.go`; the only files of `internal/app` that may import `internal/link`): `App.live` is a `liveLink` (studio: `*link.Server` or the listen error; teach: a reconnecting `liveClient` goroutine whose `State()` the UI thread reads each frame). Panels that implement `Ticker` get `Tick()` once per frame after `Jobs.Poll`. Studio (`tickStudio`): a change of `a.Scene` or of the panel's `renderRev` starts a burst and the scenario is published after 120 ms of quiet (at most 400 ms into a continuous burst) unless the model + recipe key is unchanged; `liveRenderer` renders from `meta.Recipe.Core()` with the same calls as `camera.Render`, so frames are byte-identical to `camera.exe`'s PNGs (the test/golden pair of one channel comes from one `RenderDefectPair`, the other half is kept for the next request). Teach (`tickTeach`/`adoptLive`): while `liveFollow` (default on) and the studio's scene matches the loaded model id and size, a new `(session, rev)` becomes the test source: `snapSrc.live` (+ `on`, `meta`, cleared `frames`, `p.golden = nil`), then `requestRun`, whose live branch pulls `test` (+ `good` when learning, + `golden` only when the view is golden/diff) with `liveFetch`; light, product and strokes are NOT synced. `stale` is silent, other failures show a message and retry after 2 s (`liveRetry`), a lost connection keeps the last frames, a model mismatch shows `liveMismatch` and a switch button. The capture actions (Snap, Load, the "use camera snap" checkbox) clear `liveFollow` (`leaveLive`) so a chosen capture is never replaced; `snapStale` is always false for a live source; `requestView` re-runs instead when the golden image is missing for the golden/diff view. Saving (`requestSaveSession`): the live source writes the frames it received (missing channels are pulled) with `snapfmt.WriteImage` + `snap.json`, any other source has `camera.exe` render the same description (`cameraCapture`, shared with the studio's Save); both then write `inspect.json`. The path field defaults to `defaultCaptureDir` and follows the model until edited (`snapSource.pathAuto`, kept by `resetSnap`). Loading a capture restores `inspect.json` when its model and size match (`readSessionParams`/`applyParamsFile`); the F1 window has save/load buttons for the same file.
- **Studio output** (`studio_capture.go`): the studio's right-hand Output column picks the output folder (default `captures/<model id>` next to the executable, with `/` replaced by `-`), the channels to render, whether to also write the defect-free good samples and whether to write only the description file (`snap.json.gz`, a few KB). Save runs `camera.exe` (found next to the executable or via `AFVI_CAMERA_EXE`) and writes `snap.json` plus one PNG per channel; the teach program loads such a folder with "Camera snap" -> path -> Load.
- **Virtual product and default defects**: `LoadScene` bakes `core.DefaultProductOptions()` into `Scene.Light`; `App.ApplyProduct` rebuilds it in a job and swaps in a shallow copy of `Scene` (Scene stays immutable; stale jobs drop on `a.Scene != scene`); `DefectPanel.ModelLoaded` adds ~10 `auto` strokes via `addAutoDefects` (`defect_product.go`).
- **Palette and selection**: `toolpalette.go` draws a floating palette in the `##viewer` window (a child window so it blocks canvas input) from the optional `PaletteHost` interface (unsupported tools greyed); `F11`/palette button toggles `App.focusView` (hides side panels); the defect panel implements `PaletteHost` in `defect_select.go` (selection keyed by `*core.DefectStroke`, `selectPointer`, floating editor, display-only `strokeDetected`); `PointerEvent.Ctrl`.
- **Coloured defects**: `core.DefectStroke` supports `ShapeEllipse` / `ShapePolygon` (`Points`) and an optional `Color` (R,G,B in 0..1). `RenderDefectPair` scales the stroke's blend weight by `ChannelFactor(ch)`, so each render channel stays a grayscale image but the same defect has a different brightness per channel. Uncoloured strokes must stay byte-identical to the TS reference; `DefectStroke` contains a slice so compare with `reflect.DeepEqual`, not `==`.
- **Textures**: full-resolution RGBA buffers are ~94 MB, so `pack.go` pools them (`GetRGBA`/`PutRGBA`) and packs in parallel; return buffers with `PutRGBA` once uploaded.
- **Decoupling rules** (guarded by tests): `internal/app` never imports `internal/camera`; `internal/camera` never imports `internal/inspect` or `internal/app`; `internal/core` imports none of snap/model/camera/inspect; `internal/snap` imports only the standard library and `internal/core`; `internal/inspect` stays standard-library only; `internal/link` imports only the standard library and `internal/snap`, and only the live link files of `internal/app` import it (`internal/link/isolation_test.go`). In package `app` the format package is imported as `snapfmt` because the package already has a function named `snap`. A snap and the in-process render are byte-identical for the same recipe.
