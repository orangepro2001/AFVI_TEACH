# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`teach-imgui`: native Windows desktop apps (Go + Dear ImGui via `cimgui-go`, GLFW + OpenGL3) for teaching AFVI colour-inspection machines. Single Go module `afvi/teach-imgui` with two GUI programs plus a command-line camera simulator:

- `cmd/teach-imgui` -> `bin/teach-imgui.exe`, the teaching program: starts as the **operator** (guided pages 对位 -> 金板 -> 检测), the previous interface is the **admin** interface behind `File > Admin login...` (`admin` / `1`, `Log out` returns to the operator): admin pages are `对位` (ROI stage), `对位试验台` (the old synthetic-warp align bench), `金板` (the golden board, shared with the operator) and defect detection (channel, camera snap source, F1 detection parameters, learn intervals, results, probe, and the UserMask section: regions that are not inspected). Alignment is forced (see `AlignFlow` below). No painting tools, no light tab, and it never draws the simulated stroke outlines (they are the answer).
- `cmd/camera-gui` -> `bin/camera-gui.exe`, the camera studio (window title "Color AFVI Camera Studio"), an admin tool that starts locked behind the login: light & GV tab and defect-synthesis tab (render channel, virtual good unit, brush, frame tool, colour, amplitude, profile, random defects, sensor noise, view test/golden/diff, selection palette + floating editor, stroke outlines visible). It never runs the inspection; its Output column saves the current scenario by running `camera.exe`.
- `cmd/camera` -> `bin/camera.exe`, the command-line camera simulator used by both GUIs as a subprocess.

The two GUIs also talk to each other over a live link (`internal/link`, docs/LINK.md): the studio publishes its scenario and serves frames, the teach program follows it and inspects the live frames, so nothing has to go through image files; the teach program saves a session (snap folder + `inspect.json`) when asked.

Docs in `README.md` and `docs/` are written in Chinese.

Development happens on WSL2/Linux and the app is **cross-compiled to Windows**; it only runs on Windows (fonts are loaded from `C:\Windows\Fonts`, screenshots use Win32 APIs).

- **Update service (route A, done; route B is the plan).** `scripts/publish-relhub.sh` publishes the installer to the local `release-publish` service (`relhub`, ~/dev/release-publish, podman container `release-publish`, listens on `127.0.0.1:18790` with prefix `/release`, exposed by Tailscale Serve as `https://tony-ai-pc-1.tail9f7f1f.ts.net/release`), app `afvi-teach`, platform `win-x64`, channel `stable`. It coexists with the `~/afvi-latest` + Windows ssh poll path (that one still works and the standing rule below still applies). Version rule: base = the newest `v*` tag's MAJOR.MINOR.PATCH (a prerelease suffix names the tag only), `N` = commits since that tag, `patch = tagPatch*100 + N`, `versionCode = MAJOR*10000 + MINOR*100 + patch` (v0.1.0-rc2 + 11 commits = `0.1.11` / code 111; the next tag v0.1.1 = `0.1.100` / code 200). More than 100 commits between tags collides and the script refuses with "versionCode ... is not higher" -> make a tag, never fill in `-code` by hand. Flags `--channel --dry-run --notes --version --code --app --platform --url --token --git-dir --git-rev`; the token comes from `-token`/`RELHUB_TOKEN`/`$AFVI_CI_HOME/etc/relhub-token` (secret, 0600, never committed); `--git-dir` reads tags/commits from the build server's bare `src.git` so a build whose checkout is gone still gets the right version. Idempotent: the same sha256 on the channel is a no-op; publishing touches nothing else in the history. `build-wsl.sh --publish-relhub` calls it after the installer. Route B (not started): `relhub/pkg/relclient` + an `internal/updater` in `teach-imgui` doing Check/Download/run `setup.exe -silent` in-app - it needs `require relhub` (+ `replace` or `go mod vendor`) and a source the build server can fetch, and it reuses this app id and version rule.
- `ship-wsl.sh` / `ship.ps1` (hand-over, nothing runs unless asked): `commit` refuses a non-empty index, a detached HEAD and new files over 5 MB, stages the working tree (`git add -u` + the untracked files `.gitignore` does not hide, never `-A`), makes one commit (no amend, no `--no-verify`) and treats "nothing to commit" as success; `push` is `git push origin <branch>` and is never implied by `commit`; `desktop` copies `dist/.last-installer` (written by `package-wsl.sh` / `package.ps1`) or `--file` to the Windows desktop asked from Windows (`[Environment]::GetFolderPath('Desktop')` through `powershell.exe`, so a OneDrive-redirected desktop works) and compares the sha256; `fetch` downloads the build server's installer from the GitHub Release (`nightly` by default, `--ref vX`) with only curl, verifies it against the release's `SHA256SUMS.txt`, and for nightly requires the `-g<sha>` in the file name to be `HEAD` (`--any` skips this, `--wait` polls). `build-wsl.sh` commits after gofmt/vet/tests/builds and before the installer so its version is not `-dirty`.
- **Standing rule: every build / commit / push request includes the publish step.** Whenever the user asks to build ("构建", "打包"), or to commit and push ("提交", "push"), the installer must end up in `~/afvi-latest/` so the Windows scheduled task (`register-fetch-task.ps1` -> `wscript.exe` -> `fetch-latest-hidden.vbs` -> `fetch-latest.ps1`, polls every 10 minutes over ssh; the wscript/VBS step is what keeps the 10-minute poll from flashing a console window) fetches it to the desktop by itself. Pass `--publish-latest` to `build-wsl.sh` (e.g. `./scripts/build-wsl.sh --commit "msg" --push --publish-latest`); it needs the installer, so never combine it with `--no-installer`. If the installer was built without it, run `./scripts/publish-latest.sh dist/AFVI-Teach-Setup-<version>.exe` afterwards. Commit and push still only happen when the user asks for them; this rule only adds the publish step (`--publish-relhub` is additive and independent: ask before using it in place of `--publish-latest`). This machine is native Linux, not WSL, so `ship-wsl.sh desktop` cannot work here (no `powershell.exe`): do not use it, and report that the Windows side picks the file up on its next poll (log: `%LOCALAPPDATA%\AFVI\fetch-latest.log`).
- In the maintainer's interactive zsh, `gofmt` is aliased to `gofumpt -l -w .`, which **rewrites files in the working directory**. Always write `command gofmt ...` (the build script is unaffected).

- `go vet ./...` and `go build` touch `internal/app` (cgo). They need the cross environment the build script exports: `CGO_ENABLED=1 GOOS=windows GOARCH=amd64 CC=x86_64-w64-mingw32-gcc CXX=x86_64-w64-mingw32-g++` (apt `mingw-w64`). Prefer running them through `build-wsl.sh`. First cgo build takes 2-3 min.

It also builds `bin\camera.exe` (pure Go, `CGO_ENABLED=0`) and runs the same pure-Go test set. Keep the two scripts' gofmt/vet/test steps in sync. Both one-click scripts end by building the installer (`build-wsl.sh` calls `package-wsl.sh --no-build`, `build.ps1` calls `package.ps1`; `--no-installer` / `-NoInstaller` skips it, `--version`/`-Version` and `--reference`/`-Reference` are passed through). `package-wsl.sh` without `--no-build` runs `build-wsl.sh --no-installer`, so the two never call each other in a loop. `package.ps1` builds its own `-H windowsgui` copies in `dist\bin`, so the console-subsystem `bin\` exes of `build.ps1` are not what gets shipped; the PowerShell path has only been parse-checked.

## Architecture

Packages with a strict dependency direction `app -> core, inspect, golden, config`:

- **`internal/config`**: pure Go, hand-written TOML-subset reader/writer for `afvi.toml` (machines with FM1/FM2/BM data roots). Relative paths resolve against the config file's directory (`Config.ResolvePath`). Lookup order: `-config` -> `AFVI_CONFIG` -> next to exe -> working dir. With no file, `app.Run` synthesises a `REFERENCE` machine from `FindReferenceRoot`. `afvi.toml` and `reference/` are git-ignored (machine-specific); `configs/afvi.example.toml` is the template.
- **`internal/core`**: pure Go image/algorithm code for the **simulation** (gray, rng, light, warp, align, defect strokes/painting/rendering, `RenderDefectPair`, `RenderGoodSample` = defect-free sample with sensor noise). It is a **bit-for-bit port of the TypeScript `teach-core`** from a separate repo (DMT_AFVI_Color_Parameter_AutoParse). Tests such as `TestRngMatchesTS` / `TestHashGrainMatchesTS` pin golden values from the TS implementation, and helpers like `ClampByte` deliberately mimic JS `Math.round`. Don't "improve" numerics or RNG/hash behaviour without checking against the TS reference. Keep it free of cgo and UI imports so it stays testable on Linux. The old golden-diff detection (`DetectDefects`, `ProbeArea`, `DefectParams`, `DefectReport`, thresholds, `MaterialMask`) was removed; detection now lives in `internal/inspect`. It also holds `ApplyProductVariation` / `NewProductLightScene` (`product.go`, virtual good unit baked into `LightScene.Texture`, off in all other core APIs) and `strokegeom.go` (stroke bounds / distance / point-in-shape helpers).
- **`internal/inspect`**: the inspection algorithm, standard library only (it also reads and writes the parameter file `inspect.json` in `paramsio.go`: `Params` has a named-material JSON form, `ParamsFile` holds per-channel `{learned, params}`, `WriteParamsFile`/`ReadParamsFile` validate). `Inspect(img, regions, params)` receives only the 8-bit gray test image and the product's *design* material map (unpainted `Scene.Material`: base 0, SR 1, open 2, metal 3) — never the golden/clean render, the simulated strokes or any simulation type. Per material there is an accepted GV interval `[Low, High]`; pixels outside it are flagged (above High = bright, below Low = dark), each pixel is judged on its own value (never an average); a defect is an 8-connected component of flagged pixels of one material and polarity and is reported only if it has at least max(`Size`, `MinArea`) flagged pixels (`Size` is the number of contiguous flagged pixels: with High=100 and Size=2 the row 105,106 is detected but 105,99,102 is not; no dilation, no merging; `MinArea` defaults to 1). `Params.EdgeMargin` (0..64 px) ignores every pixel whose Chebyshev distance to a pixel of a different material is at most that value: such pixels take no part in per-material statistics, `Learn`, flagging or probes (the machine's "Margine"); the library default is 0 and the app default is `defaultEdgeMargin = 6`. `Params.BackgroundRadius` (0..16, library default 0 = the plain per-material interval) together with the per-material `MaterialParams.LocalBackground` switch (true for every material in `DefaultParams`, but the app's default configuration, `newInspectParams` in the defect-product helper with `defaultBackgroundRadius = 2`, enables it for Metal only) selects the local background mode implemented in the inspect package's background file: a valid pixel of such a material is compared with the median of the same-material valid pixels in its (2r+1)² window (Huang sliding histogram), the accepted interval applies to f = (v − b) + mean(b) clamped to 0..255, statistics/Learn/Probe of that material use f, `Defect.PeakGV`/`MeanGV` stay raw; the median follows hard-edged plateaus, so large flat defects are absorbed as background (that is why SR keeps the global interval); changing the radius or the switch re-learns like the edge margin. `core` and `inspect` must never import each other; this is guarded by `internal/inspect/isolation_test.go` (inspect imports only the standard library, and no file in `internal/core` imports inspect). `internal/app/inspect_bridge.go` is the only place that converts between the two. **Tile rules** (`rules.go`, `tile.go`; spec and contract in `docs/INSPECT_RULES.md`): besides the accepted interval each material has two rules measured against the mean GV of the same material in its `TileSize`×`TileSize` tile (`Params.TileSize`, default 400, 16..4096; the grid is `n=W/T`, tails below half a tile merge into the last tile; `Params.TileSmooth` interpolates the reference bilinearly between tile centres; a tile with fewer than 64 valid pixels pools its 3×3 tile neighbourhood, then the global material mean; edge-margin pixels take no part): `MaterialParams.Abs` ("Offset 1", bright `v > ref+Bright`, dark `v < ref-Dark`, GV) and `MaterialParams.Pct` ("Offset 2", bright `v > ref*(1+Bright/100)`, dark `v < ref*(1-Dark/100)`), each a `TileRule{Enabled, Bright, Dark, BrightSize, DarkSize}` (an offset <= 0 disables that polarity) — with the two bright/dark offsets and the two bright/dark minimum contiguous sizes that is 8 new parameters per material. Every rule and polarity has its own 8-connected size filter `max(rule size, MinArea)`; the accepted pixels of all rules are OR-ed and regrouped into defects whose `Defect.Rules` bitmask (`RuleInterval|RuleAbsolute|RulePercent`) says which rules flagged them; `MaterialParams.IntervalOff` switches the interval rule off; `MaterialStats.Tiles/TileMeanMin/TileMeanMax` report the grid. All tile rules are off by default (library and app): on a non-uniform good unit they flag a lot (SR: 10% of a mean of 16 GV is below its own noise), so the user opts in per material. `Learn` keeps the rules; the parameter file stores them (`abs`/`pct`/`intervalOff` per material, `tileSize`/`tileSmooth`), old files load with the defaults. `Inspect` of a 5860×4020 image takes about 0.5 s interval-only and 0.6-1.4 s with tile rules.
- **`internal/golden`**: the golden board (金板), pure Go, standard library only (docs/GOLDEN.md). The inspected area is a **mask**, not the whole object: `Mask` (one byte per pixel on the design grid), `Threshold` (grey range in/out), `Erode`/`Dilate` (separable square window, `MaxPad` 64), `Open`/`Close`, `And`/`AndNot`, `Shape` (rect/ellipse/polygon) with `Add` (optional min GV: only pixels at or above it are added) / `Erase`, `AreaFilter` (min area, fill holes), `AutoRange`, `MaskFromMaterial`, and the derivation `InspectMetal(metal, padding)` (Metal mask eroded by Padding, `DefaultPadding` 4), `AutoSR(srLayer, metal, inset)` (= `AndNot(Erode(sr, inset), Dilate(metal, inset))`, `DefaultSRInset` 4) and `Material(metal, sr)` (3 inside the padded Metal, 1 inside SR, 0 elsewhere = the material map `internal/inspect` receives). `UserMask` (`usermask.go`: `Region{Target, Shape}` with `TargetMetal` / `TargetSR`, `With`/`Without`/`WithoutTarget`/`Rasterize`, and `ApplyUser(metalInspect, sr, u)` which removes the Metal regions from the inspected Metal only and the SR regions from the inspected SR only; at most `MaxRegions` 256). `Save`/`Load` write `golden.json` (+ the optional `userMask` array, absent when empty) + `golden-metal.png` (sha256 of the pixels, verified on read). `internal/inspect` and `internal/core` never import it (`isolation_test.go`).
- **`internal/model`**: pure Go model scanning/loading moved out of the cgo package `internal/app` (`ScanMachine`, `LoadScene`, `Scene`, `ResolveConfig`, `FindModel`); `internal/app` keeps thin aliases. `internal/model/modeltest` writes a tiny synthetic reference tree for tests.
- **`internal/snap`**: the shared capture format, standard library plus `internal/core` only. A capture is a folder with a description file `snap.json` (also readable as a single `*.json` or gzip `*.json.gz`; unknown fields ignored; `version` 1) plus 8-bit gray PNGs `red.png`, `green.png`, `blue.png` (kind `test`) and `red-good.png`... (kind `good`, a defect-free sample used for learning). `snap.json` carries all meta information (`format` `afvi-snap`, `version`, `producer`, `created`, `model` with the absolute layer paths, `width`, `height`, `recipe` with product/light/noise/defects/sceneStrokes, and `images` with channel, kind, file, size and the sha256 of the raw pixels, verified on read). With `-mode recipe` only the description is written (a few KB, dense when gzip-compressed) and any consumer can re-synthesise identical pixels deterministically. **Scenario file** (`scenario.go`, `xml.go`; docs/SCENARIO.md): `afvi-scenario` XML (`.xml` or gzip `.xml.gz`, `encoding/xml`, attributes, enum names, floats round-trip exactly) holding everything the camera studio has set: the recipe (light mix, virtual good unit, noise, warp), ALL strokes in panel order with their enabled/auto flags (the recipe lists derived by `Scenario.Meta()` contain the enabled ones only) and the studio UI state (`Studio`: view, channel, tool, brush, random generator, default-defect settings, output settings). `snap.ReadMeta`/`Unmarshal` read it like a capture description (a folder without `snap.json` falls back to its `scenario.xml`), `WriteMeta` writes XML for `.xml`/`.xml.gz`, so every consumer of descriptions (teach program, `camera.exe -in scenario.xml`) accepts it.
- **`internal/link`**: the live link contract between the two GUIs, standard library plus `internal/snap`; docs/LINK.md is the spec. Framed TCP (20-byte header `AFVL`/version/type/id/JSON length/body length, JSON part + binary body). The studio side is `Server` (`Listen`, `Publish(meta, render) rev`, `Peers`, `Rev`, `Close`): it pushes the current `Scene{Rev, Meta}` (a `snap.Meta` without images) after the hello and after every publish (coalesced) and answers `getFrame{rev, channel, kind}` with raw 8-bit gray frames, `kind` = `test` | `good` | `golden` (the clean render, only for the golden/diff views); a request for a revision that is no longer current gets `stale` (also re-checked after rendering), at most 2 renders run at once and 4 frames per revision are cached. The teach side is `Client` (`Dial`, `Scene`, `Updates`, `Frame(ctx, rev, channel, kind)`, `Done`, `Err`); reconnecting is the caller's policy (the app redials every 2 s). A studio process has a random session id, revisions are only comparable within one. Loopback only, no authentication.
- **`internal/access`**: roles and the login, pure Go and standard library only. `Role` is `RoleNone` / `RoleOperator` / `RoleAdmin`; `Authenticate(user, password)` trims and case-folds the user name, maps `admin` + `1` -> `RoleAdmin`, `operator` + empty password -> `RoleOperator`, and returns `(RoleNone, false)` otherwise. Passwords are compared as SHA-256 digests with `crypto/subtle.ConstantTimeCompare` (only the digest is stored), but the built-in accounts only separate the two audiences - they are not a security boundary (local, unsigned exe).
- **`internal/camera` + `cmd/camera`**: the camera simulator, pure Go (`CGO_ENABLED=0`, builds and runs on Linux and Windows). `DefaultRecipe`, `Render`, `Save`, `SceneFromMeta` and the command line `Main`. The default scenario equals the app default: nominal virtual good unit, red/green/blue lights at 512, no sensor noise, 10 tiny bright specks (seed 7) from the shared generator `core.DefaultTinyDefects` that the app also uses. Command line: `camera -ref <reference> -list`; `camera -ref <reference> -model FM1/25fbo015-15 -channels red,green,blue|all [-good] [-count N -seed N -strength X -no-product -noise-read S -noise-shot G -noise-seed N] [-dx -dy -rot -scale -shear-x -shear-y -tilt-x -tilt-y -bend -bend-wave] -out <folder>`; `-mode recipe -out desc.json.gz`; `-in <snap.json|desc.json.gz|folder> -out <folder> -channels blue` (re-render a description; without `-model` the layer paths stored in the description are used; an output folder that already holds the same recipe keeps its earlier images); `-info <path>`; `-config/-machine/-ref` as in the teach app. Exit codes: 0 ok, 1 runtime failure, 2 usage. The built-in default scenario is slightly misaligned: `core.DefaultCaptureWarp()` = shift (14, -10) px, rotation 0.3 deg (`camera.DefaultRecipe` applies it, and so does the teach program's built-in simulated capture); `-aligned` renders the built-in default scenario exactly in place (identity warp, no `warp` field, byte-identical to the old default) and is ignored together with `-in`, while explicitly given geometry flags still override field by field. The camera studio's own default stays aligned because painting needs it; its warp presets gained 典型错位（相机默认）. Misalignment / lift: the warp flags (`warpflags.go`, only explicitly given flags override the recipe's warp, so they combine with `-in`) fill the optional `snap.Recipe.Warp` (omitted when the geometry is the identity, so older descriptions stay byte-identical); `Render` calls `core.RenderDefectPairWarped` (golden and test, defects included, warped as one product, sensor noise added afterwards; the good sample stays nominal because it is the taught reference). `core.WarpParams` gained `TiltX/TiltY` (perspective lift `u/(1 + a·u)`, applied after rotate/scale, before translate/bend; zero keeps the TS golden values) and `core/capture_warp.go` holds the capture limits (`ValidateCaptureWarp`, also run by `snap.Meta.Validate`). Inspection still only sees the design material map, so a misaligned capture needs aligning first: the teach program forces the `AlignFlow` (design-picture ROIs confirmed by the user) and aligns every capture with `core.AlignCapture` before inspecting.

### How `internal/app` fits together

- **Manual control** (`manual.go`): the teaching program's defect tab has a "Manual control" section. `DefectPanel.manual` (default off) makes `requestRun` refresh the test image only and clear `lastReport`; `requestInspect` (Inspect button, F5, and `requestRelearn`) sets `inspectNow` so the next run learns and inspects even in manual mode. "Load Image..." (`pickImageFile`: `GetOpenFileNameW` in `filedlg_windows.go`, a stub elsewhere) loads a PNG/JPEG/BMP/TIFF through `readGrayImage` into `DefectPanel.user` (size must equal the model); it has priority over live, snap and simulation sources, calls `leaveLive`, is dropped by `clearUserImage` (new model, snap, snap load, live adoption, "Use simulation") and is learned from itself because it has no good sample. Inspection still receives only the gray test image and the design material map.

- **Panels and roles** (`Panel` interface in `app.go`; docs/ROLES.md): each `panel_*.go` registers itself from `init()` via `registerPanel(order, ctor, profiles...)` and also registers its translations from `init()` via `Messages(zh, en, ko)`. Passing no profiles registers the panel for every program; passing profiles restricts it to those. Page management is **default deny**: `registerPanel` now means admin-only, and `registerPanelFor(roles []access.Role, order, make, profiles...)` binds a page to roles (the ids/orders are `light` 0 admin studio, `roi` 1 admin teach, `op-align` 1 operator teach, `align` 2 admin teach (对位试验台), `golden` 3 admin+operator teach, `op-inspect` 4 operator teach, `defect` 4 admin both). `App.allPanels` holds every panel for the profile and `App.panels` only the pages visible to the current `role` (same order, `a.tab` indexes it); broadcasts (`ModelLoaded`, `LightChanged`, `Tick`, `Close`) go over `allPanels`, drawing/dialogs/palette/input over `panels` only. `SetRole`/`TryLogin`/`OpenLogin`/`Logout`/`Lock`/`ShowPage`/`PageVisible`/`panelByID` manage this; hidden pages cannot be switched to or drawn, and `OpenConfigDialog`/`ApplyConfig`/`SelectMachine`/`RescanModels` are no-ops unless the role is admin. The login dialog (`login.go`) is a modal with a masked password field; `-login user:password` is the start-up form of it, and `-selftest` logs in as admin itself.
- **Profiles** (`profile.go`): `Profile` selects which program is running, `ProfileTeach` or `ProfileStudio`; `Profile.WindowTitle()` gives the OS window title (also used by the self-test to find the window for screenshots) and `Profile.defectMode()` says what the shared `DefectPanel` does: `modeDetect` (teach: adjust inspection parameters and inspect the test image, no painting tools, never draws the simulated stroke outlines) or `modeAuthor` (studio: paint the synthetic defects, product and noise and write captures, never runs the inspection). The teach program has the operator 对位/检测 pages and the admin 对位/对位试验台/缺陷检出 pages; the studio (admin only, behind the login) has the light & GV and defect-synthesis tabs.
- **Font scaling** (`scale.go`): layout constants were designed for a 13 px font; the UI font is larger now, so every hard-coded pixel length is passed through `sc()` (and `SetFontPx` sets the size once before the first frame, clamped to 10..28 px, default 16). New pixel constants must go through `sc()` too.
- **Shared state** lives on `App`: loaded `Scene` (treat as read-only), shared `core.LightSetting`, the single `Viewer`, and `Jobs`. Panels get `ModelLoaded` / `LightChanged` / `Activate` / `Deactivate` callbacks; the viewer shows one texture at a time and the active panel supplies overlays and receives left-drags in image coordinates (`Pointer`).
- **Threading model** (`jobs.go`): everything UI runs on the main OS thread (`main.go` locks it; GLFW/OpenGL require that). Heavy work goes through `App.Jobs.Run(key, work)`, where `work` runs on a goroutine and returns an *apply closure* that `Jobs.Poll` executes on the UI thread. Only apply closures may touch app/panel state. Each key has at most one job in flight, and a newer submission replaces the pending one (so slider drags render the latest value only). Panics in `work` are recovered and surfaced in the status bar.
- **Layout** (`App.Frame`): a fixed layout of non-movable, non-resizable ImGui windows positioned with `place(...)` inside the main viewport (menu bar, toolbar, tab strip, left panel, viewer, right panel, status bar). `loop` in `run.go` explicitly clears `ConfigFlagsViewportsEnable`, because otherwise edge panels become separate OS windows.

- **i18n** (`i18n.go`): `T(key, "name", value, ...)` falls back from the current language to `zh`, then to the key itself. Widgets take a stable `id` separate from the translated label so state survives language switches; keep that convention when adding controls. Add every new key to all three dictionaries (zh, en, ko).

Panels whose `Pointer` always returns true (light) must keep ignoring unknown `PointerKind` values.

A panel may additionally implement `DialogPanel` (`DrawDialogs`, called from `App.Frame` for the active panel); the defect tab uses it for the F1 detection-parameter window.

The golden image only feeds the display views (golden/diff); inspection never receives it. Changing the light does not re-learn, so over-/under-kill becomes visible. In detect mode the run is gated by the forced alignment (`AlignFlow`, see the "Forced alignment" bullet below): the raw capture becomes `p.raw`, only a usable `core.AlignCapture` result becomes `p.test` and is inspected, and the admin page shows the aligned picture (raw before confirmation). The teach profile's default `warp` is `core.DefaultCaptureWarp()`. In `modeAuthor` (studio) the panel only renders the synthetic scene and never calls `inspect`.
- **Live link** (`live.go`, `live_studio.go`, `live_teach.go`, `teach_save.go`, `live_selftest.go`; the only files of `internal/app` that may import `internal/link`): `App.live` is a `liveLink` (studio: `*link.Server` or the listen error; teach: a reconnecting `liveClient` goroutine whose `State()` the UI thread reads each frame). Panels that implement `Ticker` get `Tick()` once per frame after `Jobs.Poll`. Studio (`tickStudio`): a change of `a.Scene` or of the panel's `renderRev` starts a burst and the scenario is published after 120 ms of quiet (at most 400 ms into a continuous burst) unless the model + recipe key is unchanged; `liveRenderer` renders from `meta.Recipe.Core()` with the same calls as `camera.Render`, so frames are byte-identical to `camera.exe`'s PNGs (the test/golden pair of one channel comes from one `RenderDefectPair`, the other half is kept for the next request). Teach (`tickTeach`/`adoptLive`): while `liveFollow` (default on) and the studio's scene matches the loaded model id and size, a new `(session, rev)` becomes the test source: `snapSrc.live` (+ `on`, `meta`, cleared `frames`, `p.golden = nil`), then `requestRun`, whose live branch pulls `test` (+ `good` when learning, + `golden` only when the view is golden/diff) with `liveFetch`; light, product and strokes are NOT synced. `stale` is silent, other failures show a message and retry after 2 s (`liveRetry`), a lost connection keeps the last frames, a model mismatch shows `liveMismatch` and a switch button. The capture actions (Snap, Load, the "use camera snap" checkbox) clear `liveFollow` (`leaveLive`) so a chosen capture is never replaced; `snapStale` is always false for a live source; `requestView` re-runs instead when the golden image is missing for the golden/diff view. Saving (`requestSaveSession`): the live source writes the frames it received (missing channels are pulled) with `snapfmt.WriteImage` + `snap.json`, any other source has `camera.exe` render the same description (`cameraCapture`, shared with the studio's Save); both then write `inspect.json`. The path field defaults to `defaultCaptureDir` and follows the model until edited (`snapSource.pathAuto`, kept by `resetSnap`). Loading a capture restores `inspect.json` when its model and size match (`readSessionParams`/`applyParamsFile`); the F1 window has save/load buttons for the same file.
- **Studio output** (`studio_capture.go`): the studio's right-hand Output column picks the output folder (default `captures/<model id>` next to the executable, with `/` replaced by `-`), the channels to render, whether to also write the defect-free good samples and whether to write only the description file (`snap.json.gz`, a few KB). The same column has a "Scenario file" section (`studio_scenario.go`): the studio snapshots its whole state (`scenarioSnapshot`) into `captures/<model id>/scenario.xml` (path editable; `AFVI_CAPTURES` moves the root), autosaves it 0.5 s after a change when "remember" is on, restores it when the model is loaded (`scenarioModelLoaded`, called at the end of `ModelLoaded`; the self-test turns remember off), and has Save/Load buttons; a scenario of another model id or image size is rejected before anything is applied. `requestSaveCapture` also writes `scenario.xml` into every capture folder. The teach program loads such a file or folder with "Camera snap" -> path -> Load and **renders it in-process when camera.exe is missing** (`snap_local.go`: `localFrames` re-bakes the virtual good unit for the description's product when it differs from the loaded scene and renders through `liveRenderer`, so the pixels equal camera.exe's; `snapFetch` takes the scene for that; the session save uses `saveLocal`).
- **Virtual product and default defects**: `LoadScene` bakes `core.DefaultProductOptions()` into `Scene.Light`; `App.ApplyProduct` rebuilds it in a job and swaps in a shallow copy of `Scene` (Scene stays immutable; stale jobs drop on `a.Scene != scene`); `DefectPanel.ModelLoaded` adds ~10 `auto` strokes via `addAutoDefects` (`defect_product.go`).
- **Align panel and warp UI**: the default view is `overlay` (`PackOverlay`: template in red, warped input in green+blue) so the warp parameters show without running anything; the ROI template is by default the imagined *design picture* (`AlignPanel.tplSource` = `tplDesign`, `core.DesignTemplate` in `core/align_design.go`: every pixel painted with the MEDIAN mean of its material from the design layers, area-downsampled, blurred `DesignBlurPx`, then registered to the MEDIAN once through a 6x5 window grid + RANSAC because the layers sit 2-6 full px off the real picture; cached in `AlignPanel.design` per scene/source/scale/light/channel) so a ROI on a featureless spot is no longer found, while `tplImage` keeps the old same-picture template (every ROI matches at NCC 0.99); the input is always the warped real picture, and the grey-difference / `CheckRealigned` numbers measure against `AlignPanel.reference` (the real un-warped picture), never against the shape-only template; `align_view.go` draws, per ROI, the design box (grey), the true box (`core.WarpPoint` of the ROI centre with the current scaled params, cyan), the alignment result (`ApplySimilarity(fit, centre)`, coloured by truth error) and the match dot, plus the legend; the verdict block compares the verdict with the truth via the pure-Go `core.TruthLevel` / `core.JudgeAgainstTruth` (`align_truth.go`: correct / missed / false-alarm / strict / cautious) and shows set/measured/difference through `core.TruthPose` / `core.FitPose` (centre shift, because `WarpParams.Tx/Ty` and `Similarity.Tx/Ty` are relative to different origins). Every length is shown in full-resolution pixels and the OK/NG thresholds are converted the same way (`fullPx`), because the matching thresholds work in the working resolution. `AlignPanel.reportParams/reportW/reportH` snapshot what the report was computed for, and `reportKey` (`alignKey`: warp, occlusions, ROIs, scale, source, matching config, light) is compared with `inputKey()` to decide whether the report is stale (a finished job only clears `dirty` when its key still equals the current inputs, so a 30 s pyramid-1 run cannot present an old result as current). `core.DiagnoseRois` (truth based: match error, deviation from the fit, how far the true window leaves the image, share covered by occlusions) feeds the match-error column, the per-ROI diagnosis lines (`roiNotes`) and the names/numbers in the verdict reasons. `AlignConfig.MinOverlap` (default 0.9, UI slider; 0 or >= 1 = old behaviour) lets `nccAt` score a window that is only partly inside the image over the overlap, because the machine ROIs P4-P7 sit flush in the image corners and a shift toward the corner would otherwise leave their true window outside (they could only match clipped at the border and became outliers -> MANUAL); `RoiMatch.Overlap` reports the share inside at the found position, `core.MatchCost` drives the "this run will be slow" hint (pyramid 1 + radius 230 took ~34 s). `warp_ui.go` holds the presets (`warpPresets`, geometry only via `setWarpGeometry`) shared with the camera studio's "Misalignment & Lift" section; the studio keeps the warp in `DefectPanel.warp` (flows into `snapMeta`, `snapStale`, every in-process render and the live renderer) and, while it is not the identity, disables painting/selecting (`Pointer`, `PaletteSupports`, overlays) because strokes live in the product's own coordinates. The aligned views (`aligned`, `alignedOverlay`, `alignedDiff`, `isAlignedView`) show the input resampled onto the template grid by `core.RealignInput(input, *report.Fit, occlusions)` — only the input and the fit the algorithm found, never `WarpToSimilarity` of the set warp — held in `AlignPanel.aligned` (`alignedResult`: image + validity mask, grey difference before/after through `core.MeanAbsDiff`, and `core.CheckRealigned`, a 5x4 grid of template windows re-matched on the realigned image to measure the leftover shift of the whole picture, which a ROI-only residual hides because a similarity fitted to a few points extrapolates badly). `alignFit()` only offers the fit while `fitInput == input` (the input image the report was computed from; a regenerated input drops it), `alignedNow()` additionally requires the cached image to be made from that input and fit, and the run job always builds it when a fit exists so `requestView` can reuse it. The overlay in these views maps the true window and the match points back through the inverse fit and marks the worst check window (`Viewer.ZoomOn`, 4x).
- **Golden board** (`golden_board.go`, `golden_jobs.go`, `golden_refine.go`, `golden_pack.go`, `panel_golden*.go`; `App.golden`, nil in the studio; docs/GOLDEN.md): `goldenBoard` owns the drawn Metal mask, the binary range (requested `low/high/out` vs applied `appLo/appHi/appOut`), Padding, SR inset, a 6-step history (mask + range only) and the derived result (`goldenDerived`: `metalInspect`, `sr`, `material`, `classes`, counts). ALL work goes through ONE job key `golden` with a strict op queue (`Jobs.Run` replaces a pending job, so the board queues ops itself and coalesces consecutive range/derive/source/repack ops), a generation counter `gen` drops stale results and `rev` is bumped for every applied derived result (`learnRev` = `rev` without the UserMask edits, `alignRev` = only changes of the drawn Metal mask). Geometry (`goldenBuildGeometry`): `core.DesignTemplate` registers the design layers to the golden sample picture once, `core.WarpMaterialToReference` moves the design material map onto it, `srPic = goldenSnapSR(...)` limits the SR layer to the pixels that look like SR in the picture (`goldenRefineSR`: grey band mean ± max(4σ, 6) of the layer interior, never grows, falls back to the layer when the result is below 70%; without it SR needed an inset of 8 to be overkill free, with it 2 is enough). The first build is automatic (`goldenAutoMetal`: `golden.AutoRange` between the Metal and SR means, then Open 1; a flat channel falls back to the design Metal layer). `App.inspectRegionsFor(scene)` returns the golden material map once the board is ready (else the design map): `DefectPanel.requestRun` snapshots it before the job, relearns when `goldenRev` (= `LearnRev()`) changed, and blocks inspection while the board is not ready (`InspectBlocked`). With a golden board the default `Params.EdgeMargin` is 0 (`DefectPanel.freshParams`; Padding does that job, `defaultEdgeMargin` 6 stays for the legacy flow). The alignment template follows the board: `core.PaintedTemplate(classes, nominal, scale)` (class map painted from the drawn Metal, `srReal`, the design Open layer; area downsampled and blurred, NOT registered again) replaces `core.DesignTemplate` when the board is ready, `AlignOutcome.GoldenRev` / `alignTemplate.goldenRev` record which board it was made for and `AlignState()` is `alignWorking` when it differs from `g.AlignRev()` (with the design-layer template the aligned capture still sat up to ~8 px off the mask on the reference model, now at most 1-2 px). **UserMask** (`panel_defect_usermask*.go`, `DefectPanel.um`, detect mode only; the name is the same in all three languages): the admin defect page draws regions (rect/ellipse/polygon through a `FrameTool`, tool state `userMaskUI`, Esc stops it) that are NOT inspected, a Metal region removes only inspected Metal pixels and an SR region only inspected SR pixels (`golden.ApplyUser`, applied last in `goldenDerive`, so `derived.metalInspect`/`sr`/`material` are the FINAL inspected areas, `userMetalPx`/`userSRPx` count what was removed). It lives on the board (`goldenBoard.user`, ops `opUserAdd/Remove/Clear`, `AddUserRegion`/`RemoveUserRegion`/`ClearUserMask`), is saved with the board (`userMask` array of golden.json) and a UserMask edit changes `rev` only: no re-alignment, no re-learning of the user's intervals. Drawing is only offered when the board is ready and the alignment is done (the picture is then on the design grid). The golden page paints only the final inspection area (default colour magenta, SR green); the padding band is an opt-in blue layer (an orange band made users read the ring, not the magenta area, as the mask). Pages: `golden` order 3, registered for both roles with `HidePalette()`; the operator `op-align` page's next button goes to it. Measured on the reference model (FM1/25fbo015-15, defect-free aligned unit): Padding 2 -> 101 false Metal defects, 3 -> 12, 4 -> 0; SR inset 4 -> 0 (13 without the snap). Selftest trap: `gotoPage` calls the page's `Selftest()`, which seeds ~11 test strokes, so a step that needs a defect-free image must clear `dp.strokes` AFTER `gotoPage`.
- **Forced alignment** (`align_flow.go`, `defect_align.go`, `panel_align_flow.go`, `panel_op_inspect.go`): the teach program owns one `AlignFlow` (`App.align`, nil in the studio): the ROIs live in full-resolution design coordinates, start as a clone of `scene.MachineRois`, and are confirmed with `Arm()` (at least 2 ROIs); editing ROIs or config (`SetRois`/`ResetRois`/`SetConfig`/`SetScale`) or loading a model (`modelLoaded`) disarms them. `DefectPanel.requestRun` (detect mode only) aligns the raw capture first: the template is `core.DesignTemplate(scene.Material, core.RenderChannel(...), scale)` (cached per scene/channel/light/scale), `core.AlignCapture` returns the full-resolution capture resampled onto the design grid with `ReplicateNoData` (nearest valid pixel, no black border) plus a `NoData` mask (the border the shift opened and the outer `core.AlignBorderPx` = 8 px frame), and `p.test` becomes the aligned image only when the outcome is usable; the inspection of the aligned image gets that mask as `inspect.Regions.Skip` (such pixels and the `EdgeMargin` around them are ignored like edge-margin pixels, `DefectPanel.testRegions`), otherwise the replicated border would be flagged as dark SR on a good unit; inspection is blocked (`InspectBlocked`) while the flow is disarmed or the alignment failed, and a new raw capture re-aligns automatically. Only the aligned 8-bit image and the design material map ever reach `internal/inspect`. The admin `roi` page is the engineering view (match table, sliders, design/raw/aligned/overlay views); the operator `op-align` page is the guided variant (draw/move/delete, 确定对位, 恢复默认框, status badge), and `op-inspect` is the guided detection page (R/G/B, big 检测 button, OK/NG verdict, short defect list, no parameters). The design template is rendered with the light of the capture: `alignTemplateLight(a.Light, meta)` (`align_light.go`) takes the description's light (`meta.Recipe.Core().Light`) when the capture is a live link / camera snap and `a.Light` otherwise (simulation, Load Image). The teach program's `a.Light` starts as `core.DefaultCaptureLight()` (R/G/B 512, white off, the same light as `camera.DefaultRecipe`; `core.DefaultLightSetting()` is red only and stays the studio's default), because with a red-only light the green/blue nominal render is all black, the template is flat and the machine ROIs could never be located on those channels. `AlignOutcome` records `Channel`, `TplFlat` and `RawFlat` (`imageFlat`: the 5th..95th percentile span of the grey values is below `flatRangeGV` = 3, so sparse defect specks do not count as contrast), and `explainAlign(out, drawn)` (`align_explain.go`, texts `alignx.*`) turns a failed outcome into the plain-language text of the operator page, the admin ROI page and `DefectPanel.alignReason` (drawn vs located boxes, channel, one cause, one hint); the self-test steps `flow-channel-green/blue` (aligns G and B) and `roles-flat-channel` (renders the failure on the operator page) guard it.
- **Defect-page sub-tabs** (`defect_focus.go`, `defect_focus_pack.go`, `panel_defect_focus.go`, `widgets_segment.go`, texts in `defect_focus_text.go`; detect mode only, never in the studio): the admin defect page has a second-level strip `Metal | SR` (literal names, colour chips magenta / green, counts from the last report) between the page tabs and the three columns. `App.Frame` knows it through the optional `SubTabPanel` interface (`SubTabs`, `SelectSubTab`, `SubTabNote`; `SubTabStrip` in `widgets_segment.go`): a page that returns items reserves a band of `FrameHeight()+sc(10)` and the columns start lower, other pages keep the old layout. The selection is `DefectPanel.focus` (`defectFocus{target golden.Target, polarity}`, zero value Metal / all) and drives: (1) the viewer tint: the "test" view is packed with `PackGrayTint` (35 % of magenta over `derived.metalInspect` or green over `derived.sr`, the FINAL inspected masks) only when the board is Ready and not Empty, the alignment is done (`userMaskDrawable()`) and the view is "test"; `requestRun` decides inside the job (`tint.on() && (!required || test == aligned)`), `requestView` on the UI thread, and every apply closure compares `focusTintKey()` with `p.tintShown` and repacks through `requestView` when they differ (`tintKey.rev` is only meaningful when `on`, otherwise an off key ping-pongs forever; the snapshot target, not the current one, is what a job stamps); (2) the UserMask target (`p.focus.target`; the Metal / SR target buttons are gone, the three shape buttons switch the tool on and off); (3) the right column: the defect table and the viewer's defect boxes only show `focus.material()` and the polarity filter `全部 / 过亮 / 过暗` (`focusRows()` caches the indices per report pointer and focus; totals stay unfiltered; clicking the Metal / SR row of the material table selects the tab); (4) the F1 window lists the selected material's section first with a `◀ 当前` mark. Self-test steps `defect-focus-*` (`selftest_focus.go`) assert the tint key, the rows and the SR UserMask target; the first one confirms the ROIs again because the UserMask steps leave the alignment disarmed, and the last one disarms it again for the role steps.
- **Palette and selection**: `toolpalette.go` draws a floating palette in the `##viewer` window (a child window so it blocks canvas input) from the optional `PaletteHost` interface (unsupported tools greyed); `F11`/palette button toggles `App.focusView` (hides side panels); the defect panel implements `PaletteHost` in `defect_select.go` (selection keyed by `*core.DefectStroke`, `selectPointer`, floating editor, display-only `strokeDetected`); `PointerEvent.Ctrl`.
- **Coloured defects**: `core.DefectStroke` supports `ShapeEllipse` / `ShapePolygon` (`Points`) and an optional `Color` (R,G,B in 0..1). `RenderDefectPair` scales the stroke's blend weight by `ChannelFactor(ch)`, so each render channel stays a grayscale image but the same defect has a different brightness per channel. Uncoloured strokes must stay byte-identical to the TS reference; `DefectStroke` contains a slice so compare with `reflect.DeepEqual`, not `==`.
- **Textures**: full-resolution RGBA buffers are ~94 MB, so `pack.go` pools them (`GetRGBA`/`PutRGBA`) and packs in parallel; return buffers with `PutRGBA` once uploaded.
- **Decoupling rules** (guarded by tests): `internal/app` never imports `internal/camera`; `internal/camera` never imports `internal/inspect` or `internal/app`; `internal/core` imports none of snap/model/camera/inspect; `internal/snap` imports only the standard library and `internal/core`; `internal/inspect` stays standard-library only; `internal/link` imports only the standard library and `internal/snap`, and only the live link files of `internal/app` import it (`internal/link/isolation_test.go`); `internal/installer` imports only the standard library, and `cmd/setup` / `cmd/mkinstaller` import nothing but it and the standard library. In package `app` the format package is imported as `snapfmt` because the package already has a function named `snap`. A snap and the in-process render are byte-identical for the same recipe.
